## 1. 개발 환경

| 항목 | 내용 |
|---|---|
| 엔진 | Unity 6 (6000.3.14f1), URP 2D 렌더러 |
| 입력 | Input System 1.19 (`BastionControls.inputactions`) |
| 카메라 | Cinemachine 3.1.7, URP Pixel Perfect Camera |
| 텍스트 | TextMesh Pro (Unity 6의 `com.unity.ugui`에 포함) |
| 테스트 | Unity Test Framework (PlayMode), Input System 테스트 픽스처 |
| 자동화 | Unity CLI(베타) + `com.unity.pipeline`(실험) |

### Unity CLI와 Pipeline 패키지
이 프로젝트는 대부분의 작업을 **에디터를 연 채로 터미널에서** 했습니다.

- `com.unity.pipeline` 패키지를 설치하면 실행 중인 에디터가 로컬 서버를 열고, `unity command <명령>`으로 조작할 수 있습니다.
- 자주 쓴 명령: `eval`(C# 코드 즉시 실행), `eval_file`, `run_tests`(PlayMode는 `--async_tests true` 필수), `test_status`, `editor_play`/`editor_stop`, `console`, `open_scene`, `package_add`.
- 기존 `Unity.exe -batchmode`는 **에디터가 프로젝트를 열고 있으면 실행할 수 없습니다**(프로젝트 잠금). Pipeline 방식은 이 제약이 없습니다.

> 학습 포인트: 처음 배울 때는 에디터에서 직접 하는 것이 맞습니다. 다만 "에디터에서 손으로 하는 모든 일은 코드(Editor API)로도 할 수 있다"는 점은 알아 두면 좋습니다.

## 2. 프로젝트 구조

```
Assets/
├─ _Bastion/                     직접 만든 것 전부 (앞의 _는 정렬용 관례)
│  ├─ Scripts/
│  │  ├─ Bastion.Runtime.asmdef  게임 코드 어셈블리
│  │  ├─ Core/                   상태 머신, 체크포인트, 게임 흐름, 연출 보조
│  │  ├─ Player/  Combat/  Enemy/  Boss/  Hazards/  UI/
│  │  └─ Editor/                 에디터 전용 (Bastion.Editor.asmdef)
│  ├─ Tests/PlayMode/            테스트 (Bastion.Tests.PlayMode.asmdef)
│  ├─ Data/                      ScriptableObject 수치 데이터
│  ├─ Prefabs/  Animations/  Input/  Scenes/
│  └─ Art/                       팔레트, 타일 에셋, 파생 그림
└─ ThirdParty/                   외부 에셋 원본 (수정하지 않음)
```

### 어셈블리 정의(asmdef)를 쓴 이유
| 어셈블리 | 참조 | 이유 |
|---|---|---|
| `Bastion.Runtime` | Input System, Cinemachine, TextMeshPro, UGUI, URP 2D | 게임 코드. 코드를 고치면 이 어셈블리만 다시 컴파일됨 |
| `Bastion.Editor` | Runtime, 2D Sprite Editor | 에디터 전용 코드가 빌드에 섞이지 않게 |
| `Bastion.Tests.PlayMode` | Runtime, Input System, 테스트 프레임워크 | `UNITY_INCLUDE_TESTS`일 때만 컴파일 |

> 함정: Light2D는 `Unity.RenderPipelines.Universal.Runtime`이 아니라 **`Unity.RenderPipelines.Universal.2D.Runtime`** 어셈블리에 있습니다. asmdef를 쓰면 이런 참조를 직접 맞춰야 합니다.

### 씬
| 씬 | 용도 |
|---|---|
| `Stage1` | 실제 게임 레벨 (빌드 설정에 등록) |
| `Sandbox` | 초기 이동 테스트용 회색 박스 씬 (현재는 갱신하지 않음) |

## 3. 에셋 파이프라인

### 3-1. 픽셀 아트 임포트 자동화 (`PixelSpriteImporter`)
`Assets/ThirdParty/` 아래 PNG를 넣으면 `AssetPostprocessor.OnPreprocessTexture`가 자동으로 설정합니다.

| 설정 | 값 | 이유 |
|---|---|---|
| Pixels Per Unit | 16 | 타일 1칸(16px) = 1 유닛. 모든 그림의 크기 기준을 통일 |
| Filter Mode | Point | 픽셀이 흐려지지 않게 |
| Compression | None | 색이 깨지지 않게 |
| Mesh Type | Full Rect | 타일링(Draw Mode: Tiled)과 마스크가 정확하게 |
| 슬라이스 | 경로별 규칙 | 기사 120×80, 보스 100×100, 몬스터는 정사각 스트립, 함정은 32px 가로 스트립, 타일셋 16×16, 배경은 알파 기준 자동 |

- 빈 칸(완전 투명)은 프레임에서 뺍니다.
- **최초 1회만 적용**(`userData`에 표시)해서, 이후 인스펙터에서 바꾼 값은 유지됩니다.
- 다시 슬라이스할 때 **기존 스프라이트 ID를 이름으로 찾아 재사용**합니다. ID가 바뀌면 그 스프라이트를 쓰던 애니메이션 클립의 참조가 모두 깨지기 때문입니다.
- 슬라이스는 Unity 6 방식인 `ISpriteEditorDataProvider`로 합니다(예전 `TextureImporter.spritesheet`는 폐기 예정).

### 3-2. 라이선스 관리
| 에셋 | 라이선스 | 처리 |
|---|---|---|
| Fantasy Knight, Undead Executioner | 무료, 상업 이용 가능, **재배포 금지** | `.gitignore`로 저장소에서 제외, README에 다운로드 링크 |
| Monsters Creatures Fantasy 1·2, GothicVania Church/Bridge, Animated Traps | CC0 | 저장소 포함 |

> 학습 포인트: 무료 에셋도 라이선스 조건이 다릅니다. 포트폴리오를 공개 저장소에 올릴 때는 반드시 확인해야 합니다.

### 3-3. 파생 그림 (원본은 수정하지 않음)
원본 그림이 레벨에 맞지 않을 때는 **원본 파일을 고치지 않고**, 원본 픽셀과 색만으로 새 PNG를 만들어 `Assets/_Bastion/Art/`에 두었습니다.

| 파생 그림 | 만든 방법 | 이유 |
|---|---|---|
| 촛대 기둥, 촛불 | 타일셋에서 잘라냄 | 체크포인트 비주얼 |
| 발판 밑면 (`Tiles/Platform`) | 아래 가장자리와 이어진 어둠 색만 투명 처리 (flood fill) | 떠 있는 발판 밑면이 일직선으로 잘려 보여서 |
| 바닥 끝 보정 (`Tiles/FloorEdge`) | 두 조각의 반쪽을 조합 | 벽 옆과 벽 밑에 반복해 깔아도 무늬가 이어지게 |
| 벽 블록 (`Wall/WallBlock_*`) | 원본 기둥 몸통을 바닥 팔레트로 **팔레트 교체**, 줄눈 추가 | 원본 기둥은 파란빛 진한 보라라 바닥과 톤이 달라서 |
| 벽 옆면 (`Wall/WallSide_0/1/A/B`) | 위 블록 질감 + 60° 대각선, 16×16 타일 4장 | 비스듬한 시점의 방 구석 표현. 아래 대각선 2칸(0, 1) + 위로 번갈아 쌓는 2칸(A, B, 블록 무늬 주기 32px) |

> 학습 포인트 (팔레트 교체): 픽셀 아트에서 "밝기만 곱해서" 색을 맞추면 채도까지 같이 변해 더 어색해집니다. 원본 색들을 밝기 순서대로 목표 팔레트의 색에 1:1로 대응시키는 것이 정석입니다.

## 4. 공통 설계 패턴

### 4-1. 상태 머신 (`Core/StateMachine`, `IState`)
플레이어, 적, 보스가 모두 같은 상태 머신을 씁니다.

```csharp
public interface IState { void Enter(); void Exit(); void Tick(); void FixedTick(); }
```
- `Tick`은 `Update`에서(입력 판단), `FixedTick`은 `FixedUpdate`에서(물리) 호출합니다.
- 상태 객체는 `MonoBehaviour`가 아닌 **일반 C# 클래스**입니다. 컨트롤러가 `Awake`에서 한 번 만들어 재사용합니다.
- `StateChanged` 이벤트로 애니메이션 같은 다른 컴포넌트가 상태 전이를 알 수 있습니다.

| 주체 | 상태 |
|---|---|
| 플레이어 | 지상, 공중, 구르기(대시), 공격, 피격, 사망 |
| 근접 적 | 순찰, 추적, 공격 (+ 공통: 피격, 방어, 사망) |
| 원거리 적 | 대기, 시전 (+ 공통) |
| 보스 | 휴면, 대기, 추적, 베기, 가시, 소환, 페이즈 전환, 사망 |

### 4-2. 수치는 ScriptableObject로 (`Data/`)
`PlayerMovementData`, `PlayerCombatData`, `EnemyData`, `BossData`. 코드와 수치를 분리해서, 기획자가 코드를 건드리지 않고 조정할 수 있습니다. 같은 `EnemyData` 형식으로 Skeleton과 Wizard 두 데이터를 만들었습니다.

### 4-3. 로직과 연출의 분리 (이벤트)
게임 로직은 "일이 일어났다"는 이벤트만 발생시키고, 연출은 별도 컴포넌트가 듣고 처리합니다.

| 이벤트 | 발생 | 듣는 쪽 |
|---|---|---|
| `PlayerController.AttackLanded` | 공격 적중 | `PlayerFeedback`(히트스톱, 카메라 흔들림) |
| `PlayerController.AttackStarted`, `AirJumped` | 공격/공중 점프 시작 | `PlayerAnimator` |
| `Health.Damaged / Blocked / Died / Changed` | 피해 | 컨트롤러(피격 상태), `DamageFlash`, `HealthBar` |
| `GameFlow.PlayerDied / StageCleared` | 사망/클리어 | `ScreenMessage` |

> 장점: 연출을 빼거나 바꿔도 게임 로직과 테스트가 그대로입니다. 실제로 테스트는 연출 없이 로직만 검증합니다.

### 4-4. 인터페이스로 피해 처리 (`IDamageable`)
플레이어, 적, 보스, 소환수 모두 `Health`(`IDamageable` 구현)를 가집니다. 공격하는 쪽은 상대가 누구인지 몰라도 `TakeDamage`만 호출합니다.

## 5. 플레이어

### 5-1. 입력 (`PlayerInputReader`)
- Input System의 액션을 `InputActionReference`로 연결합니다(인스펙터에서 교체 가능).
- 버튼은 **"눌린 시각"을 기록**하고, 쓰는 쪽에서 "버퍼 시간 안에 눌렸는가"를 판단합니다. 이것이 점프 버퍼, 공격 버퍼의 기반입니다.
- 조작: ←/→ 이동, ↑ 점프, Z 공격, X 구르기 (게임패드 지원)

### 5-2. 이동 물리 (`PlayerController`)
`Rigidbody2D`의 `gravityScale`을 0으로 두고 **중력을 직접 계산**합니다.

**점프 공식** (높이와 정점 시간으로 정의):
```
중력      g = 2 × 높이 / 정점시간²
점프 속도  v = g × 정점시간
공중 점프  v = √(2 × g × 공중점프높이)
```
"점프가 3.2칸 높이, 0.38초에 정점"처럼 기획 언어로 수치를 정할 수 있습니다.

| 기능 | 구현 | 수치 |
|---|---|---|
| 가감속 달리기 | `Mathf.MoveTowards`로 목표 속도에 접근 | 최고 7, 가속 70, 감속 90 (공중 45/35) |
| 가변 점프 | 상승 중 버튼을 떼면 중력 2.5배 | 높이 3.2, 정점 0.38초 |
| 빠른 낙하 | 하강 중 중력 1.7배, 최대 낙하 20 | |
| 코요테 타임 | 발판을 벗어나도 0.1초간 지상 점프 허용 | |
| 점프 버퍼 | 착지 0.12초 전 입력도 인정 | |
| 더블점프 | 공중 점프 1회, 착지 시 회복 | 높이 2.4 |
| 구르기 | 0.4초 고정 속도, 0.32초 무적, 공중 1회, **중력 적용** | 속도 8.5 |
| 경사 | 지상에서는 중력을 쌓지 않고 바닥에 붙임 (`StickToGround`) | 이동 중 아래로 4 |
| 방향 전환 | `localScale` 대신 **Y축 180° 회전** | 자식 히트박스도 함께 뒤집힘 |

**접지 판정**: 콜라이더를 아래로 0.1만큼 `Cast`해서 법선이 위를 향한(`normal.y > 0.7`) 면에 닿으면 지상입니다. 벽 옆면은 지상으로 치지 않고, 상승 중에는 발판을 스쳐도 지상이 아닙니다.

> 학습 포인트: `Rigidbody2D`의 기본 중력만 쓰면 "가변 점프", "빠른 낙하" 같은 손맛 조정이 어렵습니다. 대부분의 플랫포머는 중력을 직접 다룹니다.

### 5-3. 애니메이션 (`PlayerAnimator`)
- 이동 계열(Idle/Run/Jump/Fall/Roll)은 Animator **파라미터**로 전이합니다.
- 공격/피격/사망은 코드에서 `Animator.Play`로 **직접 재생**합니다. 타이밍을 코드가 정확히 쥐기 위해서입니다.
- 게임 로직은 애니메이션에 의존하지 않습니다. 애니메이션이 없어도 테스트가 통과합니다.

## 6. 전투

### 6-1. 공격 시간표 (`AttackStep`)
공격 한 동작을 데이터로 정의합니다.

| 필드 | 의미 |
|---|---|
| `Duration` | 동작 전체 길이 |
| `ActiveStart ~ ActiveEnd` | 판정이 살아 있는 구간 |
| `CancelTime` | 이 시점 이후 다음 콤보나 구르기로 캔슬 가능 |
| `Damage`, `Knockback`, `HitStop`, `Lunge` | 피해, 넉백, 히트스톱 시간, 앞으로 내딛는 속도 |
| `HitboxOffset`, `HitboxSize` | 판정 상자 (오른쪽을 볼 때 기준) |

3타 콤보: 10 → 12 → 22 피해. 마지막 타가 넉백과 히트스톱이 가장 큽니다.

### 6-2. 판정 (`HitboxQuery`)
판정 구간 동안 매 물리 프레임 `Physics2D.OverlapBox`로 대상을 찾고, **한 번 휘두를 때 같은 대상은 한 번만** 맞습니다(`HashSet`).

> 왜 트리거 콜라이더 대신 OverlapBox인가: 트리거는 "들어온 순간"에만 이벤트가 오고 프레임 타이밍에 따라 놓칠 수 있습니다. 판정 시간을 코드가 정하는 방식이 결정적이고 테스트하기 쉽습니다.

### 6-3. 타격감
| 연출 | 구현 |
|---|---|
| 히트스톱 | `Time.timeScale = 0`을 실시간(`unscaledTime`)으로 잠깐 유지. 겹친 요청은 가장 늦게 끝나는 쪽 기준 |
| 카메라 흔들림 | `CinemachineImpulseSource` → 카메라의 `CinemachineImpulseListener` |
| 피격 깜빡임 | 스프라이트를 잠깐 붉게 (`WaitForSecondsRealtime`이라 히트스톱 중에도 보임) |
| 공격 예고 | 공격 전 무기 주변으로 입자가 모여듦 (`AttackTelegraph`) |

## 7. 적 AI

### 7-1. 구조
`EnemyController`(추상)가 공통 기능을 갖고, 파생 클래스가 행동 상태를 구성합니다.

| 공통 기능 | 내용 |
|---|---|
| 감지 | 거리 + **벽 너머는 못 봄**(레이캐스트) |
| 이동 | 앞이 벽이거나 낭떠러지면 멈춤 (`IsBlockedAhead`) |
| 피격 | 넉백(저항 비율 적용), 공격자 쪽으로 돌아봄 |
| 방어 | `Health.BlockFilter`로 정면 공격을 확률적으로 막음 (Skeleton 30%) |
| 공격 예고 | 공격 시작부터 판정 직전까지 입자 |

| 적 | 클래스 | 행동 |
|---|---|---|
| Skeleton | `MeleeEnemy` | 순찰 → 감지 시 추적 → 사거리 안이면 공격 (0.58초에 판정) |
| Wizard | `RangedEnemy` | 제자리 대기 → 감지 시 시전 → 0.6초에 화염구 발사 |

### 7-2. 충돌 매트릭스
플레이어와 적의 몸은 **서로 통과**합니다(Physics 2D 레이어 충돌 해제). 공격은 히트박스로만 판정합니다. 투사체는 Projectile 레이어로, 플레이어와 지형에만 반응합니다.

> 학습 포인트: 트리거가 동작하려면 두 레이어가 충돌 매트릭스에서 켜져 있어야 합니다. 그래서 투사체를 적 레이어에 두면 플레이어를 맞힐 수 없어 별도 레이어를 만들었습니다.

## 9. 함정 (`Hazards/Trap`)

하나의 컴포넌트가 **대기 → 예고 → 피해 → 복귀**를 반복합니다.

- 스프라이트 프레임을 코드가 직접 넘깁니다. 피해 구간을 프레임 번호로 정하므로 **그림과 판정이 항상 일치**합니다.
- 한 번 작동할 때 한 번만 피해를 줍니다.
- **활성화된 시점부터** 대기로 시작합니다(처음에는 전역 시간 기준이라 생성되자마자 작동 중일 수 있었습니다).
- 예고 입자를 붙일 수 있습니다(화염: 불티가 위로 뿜어짐).

| 함정 | 동작 |
|---|---|
| 화염 분출구 | 분출구가 달아오름(예고) → 불기둥(피해 20). 세로 0.75배로 바닥 윗면 두께에 맞춤 |
| 벽 피스톤 | 준비 → 돌출해 밀쳐냄(피해 12, 넉백 10) |

> 학습 포인트: 이 함정 팩은 위에서 내려다본 시점의 그림이라 가시 함정은 횡스크롤 바닥과 어울리지 않았습니다. 마스크, 바닥 뒤에서 솟기 등 여러 방법을 시도한 끝에 화염으로 통일했습니다. **에셋의 시점(perspective)이 게임과 맞는지**가 에셋 선택에서 중요합니다.

## 10. 레벨 (타일맵)

### 10-1. 타일맵 구성 (`Stage1/Grid`)
| 타일맵 | 정렬 | 충돌 | 역할 |
|---|---|---|---|
| `BackgroundWall` | -100 | 없음 | 배경 벽돌 벽, 아치 창문, 촛대 벽 |
| `LevelUnder` | -1 | 없음 | 벽 뒤에 이어 깔린 바닥 |
| `Level` | 0 | 없음 | **그림용** 지형 (칠하는 곳) |
| `LevelDecor` | 0 | 없음 | 떠 있는 발판 밑으로 흩어지는 돌 조각 |
| `LevelFront` | 1 | 없음 | 지형 앞에 겹쳐 그리는 칸 (벽 옆면) |
| `Collision` | - | 있음 | **충돌 전용**, 그림 없음. `Level` + `LevelFront`에서 자동 생성 |
| `Ramp` (오브젝트) | - | 있음 | 계단 위 경사 폴리곤 충돌 |

### 10-2. 그림과 충돌을 분리한 이유
1. 바닥 덩어리 타일은 조각마다 윗면 높이가 1px씩 달라, 그림 모양대로 충돌을 만들면 이음새에 걸려 캐릭터가 멈췄습니다.
2. 이 타일셋은 **위에서 비스듬히 본 시점(3/4 뷰)**이라 바닥 윗면이 그림에 보입니다. 캐릭터는 그림의 맨 위 끝이 아니라 **윗면 안쪽**을 밟아야 자연스럽습니다.

**충돌 규칙**: `Level`과 `LevelFront` 중 하나라도 칠해진 칸을 단단한 칸으로 보고, **각 기둥의 맨 윗칸을 빼고** 충돌을 깝니다. 그러면 발이 칸 위에서 16px 아래, 즉 윗면 그림 안쪽을 밟고, 플랫폼 밑면과 벽 옆면 충돌은 그림과 그대로 맞습니다.

**자동 생성** (`Editor/LevelCollisionBuilder`): `Tilemap.tilemapTileChanged` 콜백으로 `Level`이나 `LevelFront`가 바뀌면 같은 Grid의 `Collision`을 다시 만듭니다. 칠하는 동안 여러 번 호출되므로 `EditorApplication.delayCall`로 한 번만 실행합니다. 메뉴 없이 자동으로 동작합니다.

### 10-3. 타일 사용 규칙
제작자의 레벨 예시(`ThirdParty/.../PSD/concepts.psd`)를 분석해 정했습니다. 자세한 표는 [GameDesign.md 7장](GameDesign.md)에 있습니다.

- **모든 지형은 바닥 덩어리(3×3) 하나의 언어**로 만듭니다. 높은 땅은 같은 덩어리를 높여 놓고 아래를 어둠으로 채웁니다.
- 원본의 석재 기둥과 단차 조각은 **윗면 두께(원근)가 바닥과 달라서**(바닥 22px, 기둥 10px) 쓰지 않았습니다. 같은 화면 안에서 원근이 섞이면 어색해 보입니다.
- 모든 구간은 **3칸 조각 경계에 맞춥니다**. 조각 중간에서 끊으면 이음새가 부자연스럽습니다.
- 벽은 2칸 석재 블록을 아래에서부터 쌓고, 하나 걸러 **좌우로만** 뒤집습니다. 위아래로 뒤집어 이어 붙이면 데칼코마니 같은 대칭이 생겨 오히려 어색합니다.
- 벽의 맨 아래는 바닥 앞 모서리와 같은 높이에서 끝나고, 벽 뒤에 바닥을 이어 깔아 앞 테두리와 거친 끝이 벽 밑까지 이어지게 했습니다.
- 벽 옆면은 바닥 앞 모서리에서 밝은 바닥이 시작되는 뒤 모서리(21px 위)까지 **60°**로 올라갑니다.

### 10-4. 레벨 만들기 (손으로 칠하는 순서)
레벨은 전부 **Tile Palette로 직접 칠하고, 프리팹을 끌어다 놓아** 만듭니다. 아래 순서를 따르면 `Stage1`과 같은 구조가 나옵니다.

**준비**
1. **Window > 2D > Tile Palette**를 열고 팔레트 목록에서 `Church`를 고릅니다. 위쪽은 원본 타일셋과 같은 배치이고, 아래쪽에 파생 타일(발판 밑면, 바닥 끝 보정, 벽 블록, 벽 옆면)이 있습니다.
2. 팔레트 창의 **Active Tilemap** 드롭다운에서 칠할 타일맵을 고릅니다. 어느 타일맵에 칠하는지가 그리기 순서와 충돌을 결정하므로, 칠하기 전에 항상 확인합니다.
3. 자주 쓰는 도구: 브러시(B), 사각형 채우기(U), 지우개(D), 스포이트(I, 씬에 칠해진 타일을 집음). 팔레트에서 여러 칸을 드래그하면 덩어리째 칠할 수 있습니다.
4. 브러시 상태에서 **[** / **]**는 회전, **Shift + [** / **Shift + ]**는 좌우/위아래 뒤집기입니다.

**① 배경 (`BackgroundWall`)**
- 벽돌 타일로 화면 전체를 사각형 채우기로 칠한 뒤, 아치 창문과 촛대 벽을 군데군데 덮어 칠합니다.

**② 바닥 (`Level`)**
1. 팔레트에서 바닥 덩어리(3×3)를 통째로 드래그해 집습니다. 조각은 0~2열, 4~6열, 8~10열(10~12행) 세 종류가 있으니 번갈아 써서 반복을 줄입니다.
2. **3칸 단위 경계에 맞춰** 이어 칠합니다. 조각 중간에서 끊으면 이음새가 어색합니다.
3. 덩어리 아래는 어둠 타일(1열 5행)로 맵 바닥까지 채웁니다.
4. 높은 땅: 같은 덩어리를 원하는 높이에 칠하고, 그 아래를 어둠 타일로 채웁니다. 높이 차이는 1칸 단위로 자유롭게 둘 수 있습니다.
5. 칠하는 즉시 `Collision`이 자동으로 다시 만들어집니다. Scene 뷰에서 `Collision`의 Tilemap Collider 2D 외곽선(초록)이 윗면 안쪽에 있는지 확인합니다.

**③ 떠 있는 발판 (`Level` + `LevelDecor`)**
1. 바닥 덩어리의 위 두 줄을 `Level`에 칠합니다.
2. 바로 아래 줄에 파생 타일 `Platform`(발판 밑면)을 `Level`에 칠해 아래 가장자리를 마무리합니다.
3. 흩어지는 돌 조각은 `LevelDecor`에 칠합니다. `LevelDecor`는 충돌에 포함되지 않습니다.
4. 발판 높이는 점프 높이(약 3칸)와 공중 점프(약 2.4칸)를 기준으로 정합니다.

**④ 벽 (`LevelUnder` → `Level` → `LevelFront`)**
1. `LevelUnder`: 벽이 설 자리 밑에 바닥 끝 보정 타일(`FloorEdge`)을 벽 폭만큼 반복해 칠합니다. 벽 아래로 바닥 앞 테두리가 이어져 보입니다.
2. `Level`: 벽 블록(`WallBlock_LT/RT/LB/RB`, 2×2칸)을 바닥 높이부터 위로 쌓습니다. 맨 아래 줄만 `WallBlock_*Bottom`을 씁니다. 블록 하나 걸러 `_H`(좌우 뒤집은) 블록을 써서 반복을 줄입니다. 위아래 뒤집기는 쓰지 않습니다.
3. `LevelFront`: 벽 바로 옆 칸(방 안쪽)에 옆면 타일을 아래에서부터 `WallSide_0`(바닥 높이보다 1칸 아래), `WallSide_1`, 그 위로 `A`, `B`, `A`, `B` …를 번갈아 칠합니다.
4. 오른쪽 벽의 옆면은 **같은 타일을 좌우 뒤집어**(Shift + [) 칠합니다. 팔레트에도 뒤집은 한 줄이 함께 들어 있습니다.
5. `LevelFront`에 칠한 칸도 충돌에 포함되므로, 캐릭터가 옆면 앞에서 멈춥니다.

**⑤ 계단과 경사 (`Ramp`)**
- 타일 충돌은 계단 모양이라 걸어 올라갈 수 없습니다. 계단 그림 위에 빈 오브젝트를 만들고 **Polygon Collider 2D**를 붙여 경사면을 직접 그립니다(Edit Collider 버튼으로 점 이동). 레이어는 `Ground`로 둡니다.

**⑥ 오브젝트 배치 (프리팹을 Hierarchy로 끌어다 놓기)**
| 프리팹 | 놓는 곳 | 조정할 값 |
|---|---|---|
| `Checkpoint` | 구간 시작, 보스 앞 | 첫 체크포인트가 시작 위치 |
| `Skeleton`, `Wizard` | 바닥 또는 발판 위 | 순찰 범위, `EnemyData` |
| `Traps/FireTrap` | 바닥 윗면 | `startDelay`로 여러 함정의 박자를 엇갈리게 |
| `Traps/PushTrap` | 발판 끝 | 방향(좌우 뒤집기) |
| `Boss_FallenWarden` | 보스 방 안 | `BossArena`의 `boss`, `gate`, `bossHud` 연결 |

- 보스 방: `BossArena` 오브젝트의 트리거(Box Collider 2D, Is Trigger)를 방 가운데에, 입구 `gate`를 방 입구에 둡니다. 플레이어가 트리거에 들어오면 입구가 닫힙니다.

**⑦ 카메라 범위**
- `CameraBounds`의 Polygon Collider 2D 점을 맵 바깥 경계에 맞춥니다. 카메라가 맵 밖의 빈 공간을 비추지 않습니다.

**⑧ 확인**
1. Play로 처음부터 끝까지 직접 지나가 봅니다. 점프가 닿지 않는 곳, 끼이는 곳, 함정 박자가 겹쳐 지나갈 수 없는 곳이 없는지 봅니다.
2. Test Runner에서 `Stage1TraversalTests`를 실행해 구간 통과가 깨지지 않았는지 확인합니다.

| `PlayerMovementTests` | 달리기 속도, 방향, 점프 높이, 가변 점프, 코요테 타임, 공중 점프, 더블점프, 점프 버퍼, 구르기 거리/무적/중력, 공중 구르기 1회 |

| `TrapTests` | 예고 중 피해 없음, 작동 시 피해, 주기당 1회, 피스톤 밀쳐내기 |

### 입력이 있는 테스트를 쓰는 법
Input System의 `InputTestFixture`로 가상 키보드를 만들어 `Press`/`Release`합니다. 공통 기반 클래스 `BastionInputTestFixture`가 아래 문제를 해결합니다.

| 문제 | 해결 |
|---|---|
| 에디터 창이 포커스를 잃으면 키보드가 리셋되어 누르던 키가 떼어짐 | `backgroundBehavior = IgnoreFocus` |
| `Press`는 키 하나만 바꾸는데, →(62)와 ↑(63)처럼 **같은 바이트에 있는 키**를 연달아 누르면 앞 키가 지워짐 | `HoldKeys(keyboard, Key.RightArrow, Key.UpArrow)`로 키보드 전체 상태를 한 번에 보냄 |
| 테스트가 불러온 씬이 다음 테스트로 새어 오브젝트를 밀어냄 | `[UnityTearDown]`에서 빈 씬으로 교체 |
| `[UnitySetUp]`이 `[SetUp]`보다 **먼저** 실행되어, 플레이어가 입력 시스템 초기화 전에 생성됨 | 장면 준비는 `Setup()` 오버라이드 안에서 |

### 실행
```bash
unity command run_tests --mode playmode --filter Bastion.Tests --async_tests true
```

## 15. 개발 중 만난 문제와 교훈

학생들이 실제로 겪을 만한 문제들이라, 원인과 해결을 그대로 남깁니다.

| # | 증상 | 원인 | 해결 | 교훈 |
|---|---|---|---|---|
| 1 | 컴포넌트가 로드 시 NullReferenceException | `PlayerFeedback.OnEnable`이 `PlayerController.Awake`에서 설정되는 값을 사용 | 필요한 컴포넌트를 `GetComponent`로 직접 가져옴 | **다른 컴포넌트의 Awake 순서에 기대지 말 것** |
| 2 | 바닥 이음새에서 캐릭터가 멈춤 | 타일 그림 윤곽 충돌의 1px 단차 | 충돌 전용 타일맵 분리 | 그림과 충돌은 분리하는 것이 안전 |
| 3 | 캐릭터가 바닥 위에 떠 보임 | 3/4 시점 타일인데 그림 맨 위를 밟음 | 맨 윗칸을 뺀 충돌 규칙 | 에셋의 시점을 이해해야 충돌을 맞출 수 있음 |
| 4 | 재슬라이스 후 애니메이션이 깨질 위험 | 스프라이트 ID가 새로 생성됨 | 이름으로 기존 ID 재사용 | 에셋 참조는 GUID/ID로 연결된다 |
| 5 | 떠 있는 발판이 저장 후 사라짐 | 스크립트가 타일을 먼저 불러온 뒤 씬을 열어, Unity가 사용 중이 아닌 에셋을 메모리에서 내림 | 씬을 먼저 열고 에셋을 불러옴 | 에디터 스크립트에서 씬 전환은 에셋을 언로드할 수 있음 |
| 6 | 플레이 중 프레임이 멈춤 (자동화 중) | 에디터 창이 백그라운드면 플레이가 갱신되지 않음 | 테스트/자동화 중에만 `Application.runInBackground = true` | 에디터 포커스도 동작에 영향을 줌 |
| 7 | 보스가 반응할 수 없는 공격을 함 | 첫 판정이 0.17초 | 0.5초 예비 동작 + 입자 예고 | 공격에는 **읽을 수 있는 신호**가 필요 |
| 8 | 생성 직후 함정이 이미 작동 중 | 전역 시간 기준 주기 | 활성화 시각 기준 | 시간 기준점을 명확히 |
| 9 | 경사에서 미끄러짐 | 마찰 0 재질 + 매 프레임 중력 누적 | 지상에서는 중력 대신 바닥에 붙임 | 플랫포머 경사는 별도 처리가 필요 |
| 10 | 벽 색이 바닥과 안 어울림 | 원본 팔레트가 다름, 밝기만 조정하면 채도가 튐 | 팔레트 교체 | 픽셀 아트 색 보정은 팔레트 단위로 |
| 11 | 벽 이음매가 데칼코마니처럼 보임 | 위아래 거울 반복 | 블록 줄눈 + 좌우만 뒤집기 | 반복 무늬는 "의도된 경계"로 숨기는 것이 자연스러움 |
| 12 | 위에서 본 가시 함정이 떠 보임 | 에셋 시점이 횡스크롤과 다름 | 화염으로 통일 | 에셋 선택 시 시점 확인 |

## 17. 알려진 한계와 남은 일
- 사운드, 타이틀 화면, PC 빌드, 플레이 영상은 아직 없습니다.
- 보스가 검은 실루엣이라 어두운 배경에서 잘 보이지 않습니다.
- `Sandbox` 씬과 `ParallaxLayer`(배경을 타일맵으로 바꾸면서 현재 미사용)는 초기 단계의 흔적입니다.
- 벽 블록은 한 종류의 반복이라 넓은 화면에서는 패턴이 보일 수 있습니다.
